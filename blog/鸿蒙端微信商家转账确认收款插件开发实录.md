# 补上缺失的拼图：为 uni-app 鸿蒙端实现微信"商家转账确认收款"插件

> 本文记录一个 UTS 插件从可行性分析、架构设计到真机验证的完整过程：为 uni-app 鸿蒙端（HarmonyOS NEXT）补上微信商家转账用户确认收款（`requestMerchantTransfer`）能力。官方插件至今只支持 Android/iOS，而鸿蒙端的难点不止"缺实现"——鸿蒙 UTS 插件根本没有应用生命周期代理机制，微信回跳的回调在插件内无法闭环。文中给出宿主转发方案、完整代码与踩坑记录，并附开源插件地址。

- 插件地址（DCloud 插件市场）：`https://ext.dcloud.net.cn/plugin?id=TODO`（发布后回填）
- demo 工程：见插件仓库 `demo-harmony-transfer/`

## 一、问题：鸿蒙端点"领取"，一点反应都没有

业务场景很常见：用户在 App 内领取推广佣金，后端生成转账单据（状态 `WAIT_USER_CONFIRM`），前端调起微信"确认收款"页面，用户在微信里点确认，钱从商户零钱到用户零钱。

现有代码的条件编译分支是这样的：

```ts
// #ifdef APP-PLUS
// Android/iOS：UTS 插件 uni-requestMerchantTransfer（官方实现）
// #endif
// #ifdef MP-WEIXIN
wx.requestMerchantTransfer(...)
// #endif
// #ifdef H5
// toast「该客户端暂不支持领取」
// #endif
```

鸿蒙端（`APP-HARMONY`）**没有任何分支**。由于 `APP-HARMONY` 与 `APP-PLUS` 是并列关系（不是包含），整段领取逻辑在鸿蒙编译时被剔除。点击"领取"后：loading 状态静默开始、三个分支全不命中、`endLoading` 永不执行 → `loading` 永久为 `true` → 后续点击全部被防重检查静默吞掉。**表现为按钮完全无效，且无法通过重试恢复**。

查官方 `uni-requestMerchantTransfer` 插件的 `package.json`：

```json
"app": {
  "js": false, "kotlin": true, "swift": true,
  "arkts": false    // ← 鸿蒙端：无实现
}
```

`arkts: false`——官方只实现了 Android（kotlin）和 iOS（swift）。这条路官方没铺，需要自己铺。

## 二、可行性：三个关键前提恰好都成立

动手前先确认了三件事：

1. **原生壳工程已内置微信 OpenSDK**。uni-oauth-weixin（微信登录）的传递依赖里带着 `@tencent/wechat_open_sdk@1.0.23`，翻它的 `d.ets`：`OpenBusinessViewReq` / `OpenBusinessViewResp` / `WXAPIFactory` 全都在，且鸿蒙 OpenSDK ≥ 1.0.5 即支持该 API——版本余量充足。
2. **微信客户端兼容性明确**。官方文档：微信 ≥ 8.0.11.34 可调起确认收款页面，低于此版本无法拉起（可提示升级）。
3. **仓内有成熟先例**。`launchWxMiniProgram`（拉起微信小程序支付）已经打通了"原生 `Reflect.set` 注入 uni 命名空间 + `WXApi.handleWant` 回调分发 + 缓存供 JS 轮询"的完整链路，照搬模式即可。

结论：可行，且工作量可控。

## 三、真正的拦路虎：鸿蒙 UTS 插件没有 HookProxy

如果做成普通 UTS 插件，最大的问题是**回调怎么回来**。

微信确认收款完成后，微信会拉回宿主 App，回跳 Want 进入 `UIAbility` 的 `onCreate`（冷启）或 `onNewWant`（热启）。在 Android/iOS 的 UTS 插件体系里，插件可以用生命周期代理拦截：

- iOS：`UTSiOSHookProxy` 协议
- Android：`UTSAndroidHookProxy` 接口

翻遍 UTS 插件官方文档，鸿蒙平台章节明确写着——**"不涉及此章节内容"**。鸿蒙 UTS 插件编译为 ArkTS 模块，但**没有**接收 `onNewWant` 的代理机制。

也就是说：插件可以发起调起（`WXApi.sendReq`），但微信回跳的 Want 插件**拿不到**，回调链路在插件内无法闭环。这大概率就是官方插件鸿蒙端一直空缺的深层原因。

### 方案：宿主转发

既然插件拿不到 Want，就让宿主转给它。插件导出一个 `handleWeChatWant(want)`，宿主 `EntryAbility` 在 `onCreate` / `onNewWant` 里调用：

```
JS 页面 requestMerchantTransfer({mchId, appId, package})
  └─ WXAPIFactory.createWXAPI(appId).sendReq(context, OpenBusinessViewReq)
       query = mchId=xxx&appId=xxx&package=<encodeURIComponent(package_info)>
       → 拉起微信确认收款页
            ↓ 用户确认/取消，微信拉回宿主
EntryAbility.onCreate / onNewWant
  └─ 插件 handleWeChatWant(want)                ← 宿主转发（唯一集成点）
       └─ WXApi.handleWant(want, 插件的 handler)
            └─ onResp: instanceof OpenBusinessViewResp
                 && businessType === 'requestMerchantTransfer'
                 → 解析 extMsg {"result":"success|fail|cancel"}
                 → 一次性回调 onMerchantTransferResult(cb)
                 → 同时写入缓存（getLastMerchantTransferResult 轮询备用）
```

一个自然的担心：宿主可能同时集成微信登录（uni-oauth-weixin），两方都调 `WXApi.handleWant(want, 各自的 handler)` 会不会冲突？不会——`handleWant` 是"解析 Want 后回调传入的 handler"，各家 handler 各自处理认识的 `resp` 类型（登录处理 `SendAuth.Resp`，本插件只认 `OpenBusinessViewResp` 且核对 `businessType`），互不干扰。实测共存正常。

## 四、API 设计：对齐官方 + 一个增强

调起字段与官方 `uni.requestMerchantTransfer` 完全对齐（`mchId` / `appId` / `package` / `openId` / `subAppId` / `subMchId` / `success` / `fail` / `complete`），方便从官方插件迁移。在此之上做了一个**官方没有的增强**——官方的 `success` 仅代表"请求发送成功"，用户在微信里到底确认没确认，官方插件是不回传的（Android/iOS 上宿主要自己去微信回调里捞）。

本插件把它变成了一等公民：

```ts
// 1) 注册一次性确认结果回调（触发后自动注销）
onMerchantTransferResult((res) => {
  // res.result: 'success' | 'fail' | 'cancel'
  // res.errMsg: 微信回传 extMsg 原文，如 {"result":"success"}
})

// 2) 调起（字段与官方一致）
requestMerchantTransfer({
  mchId, appId, package,
  success: () => { /* 页面拉起成功 */ },
  fail: (res) => { /* 未装微信/版本过低/发送失败 */ }
})

// 3) 不想用回调也有轮询式 API
const r = getLastMerchantTransferResult()   // 无结果返回 null
```

`result` 语义必须说清楚（微信官方定义）：**`success` 仅表示微信确认收款页面展示成功**，不代表用户确认成功、更不代表资金到账。业务侧请以刷新后的订单/列表接口为准。

## 五、实现要点

### 5.1 组包：query 三参数 + UrlEncode

```ts
const req = new wxopensdk.OpenBusinessViewReq()
req.businessType = 'requestMerchantTransfer'
req.query = 'mchId=' + encodeURIComponent(options.mchId)
  + '&package=' + encodeURIComponent(options.package)
  + '&appId=' + encodeURIComponent(options.appId)
await wxApi.sendReq(context, req)   // SendReqResultWrap = boolean | Promise<boolean>
```

`package` 的值是后端转账单据应答中的 `package_info`，**必须 UrlEncode**（里面有特殊字符）。

### 5.2 回调分发：instanceof + businessType 双重核对

```ts
class TransferEventHandler implements wxopensdk.WXApiEventHandler {
  onResp(resp: wxopensdk.BaseResp): void {
    if (resp instanceof wxopensdk.OpenBusinessViewResp) {
      const r = resp as wxopensdk.OpenBusinessViewResp
      if (r.businessType === 'requestMerchantTransfer') {
        // 解析 r.extMsg → 回调 + 缓存
      }
    }
  }
}
```

### 5.3 extMsg 解析：刻意避开 JSON.parse

`extMsg` 是 `{"result":"success|fail|cancel"}` 格式的 JSON 字符串。在 ArkTS 严格模式下 `JSON.parse` 的类型处理有坑（返回 `any`，转 `Record` 再取值，类型链路很不舒服）。由于取值域是**固定的三个字符串**，直接用字符串特征判断更稳：

```ts
if (extMsg.indexOf('"success"') != -1) result = 'success'
else if (extMsg.indexOf('"cancel"') != -1) result = 'cancel'
else result = 'fail'
```

`errMsg` 透传原始 extMsg，业务侧想自己解析也留了后路。零 JSON 依赖，编译期零风险。

## 六、集成：两步原生配置 + 三行业务代码

插件侧不需要任何配置（依赖声明在插件 `config.json` 里，编译鸿蒙时自动进 ohpm）。宿主要做两件事：

**① scheme 白名单**（`entry/src/main/module.json5`）：

```json5
"module": {
  "querySchemes": ["weixin"],
  "actions": ["action.system.home", "wxentity.action.open"]
}
```

**② EntryAbility 转发**（`onCreate` / `onNewWant` 各加一行）：

```ets
import { handleWeChatWant } from '@uni_modules/xyyt-wxmerchanttransfer'

onCreate(want: Want, launchParam: AbilityConstant.LaunchParam): void {
  handleWeChatWant(want)
  super.onCreate(want, launchParam)
}
onNewWant(want: Want, launchParam: AbilityConstant.LaunchParam): void {
  handleWeChatWant(want)
  super.onNewWant(want, launchParam)
}
```

> 注意引用路径：原生工程内引用 UTS 插件**编译产物**，用模块名 `@uni_modules/<插件id全小写>`（uni cli 会在鸿蒙工程内生成产物与注册代码），不要用插件源码的相对路径——原生工程里根本没有 uts 源码。

**③ 页面调用**（vue3 页面，条件编译包裹）：

```ts
// #ifdef APP-HARMONY
import { requestMerchantTransfer, onMerchantTransferResult } from '@/uni_modules/xyyt-wxmerchanttransfer'
// #endif
```

页面侧 `import` 用**插件根路径**，不要直接 `import '.../utssdk/app-harmony/index.uts'`（原因见踩坑 2）。

## 七、踩坑记录（都是真金白银的时间）

**坑 1：`arkts-no-any-unknown`。** ArkTS 严格模式不允许推断出的 `any`。`const existing = Reflect.get(uniObj, key)` 直接编译失败，必须显式标注：

```ts
const existing: Object | undefined = Reflect.get(uniObj, key)
```

**坑 2：页面直接 import `utssdk/app-harmony/index.uts` 导致 Rollup 解析失败。** `vue3` 页面如果绕过插件根导入、直接引平台实现文件，Rollup 会尝试解析其中的 `@tencent/wechat_open_sdk`（ohpm 包）而失败：

```
[vite]: Rollup failed to resolve import "@tencent/wechat_open_sdk" ...
```

正确姿势：`import ... from '@/uni_modules/<插件id>'`，让 uni-uts-v1 按平台路由。这个坑官方文档的 `uni-app-x` 示例容易误导人（它写的是平台路径）。

**坑 3：hilog 抓不到 native 模块日志。** 打包后想看原生注册日志，`hilog -x` 里翻不到（域过滤/轮转原因未深究）。更可靠的取证方式：解包 HAP（`Expand-Archive`），在 `ets/modules.abc` 字节码里直接搜字符串常量——`uni-merchant-transfer`、`requestMerchantTransfer`、`OpenBusinessViewReq` 全部命中，确认新代码已编进包。

**坑 4：`hdc install -r` 更新不了 JS 产物。** DCloud 运行时首启会把 www 解压到应用私有目录，覆盖安装不清私有目录副本，改动"看起来没生效"。必须 `uninstall` 后 `install`（代价是清应用数据）。

**坑 5：`success` 语义误解。** 调起成功 ≠ 确认成功 ≠ 到账。三个概念，三个不同的确认时机（sendReq 返回值 / extMsg 回调 / 列表接口），别混为一谈。

## 九、结语

鸿蒙生态的第三方 SDK 适配，很多"缺位"不是技术不可行，而是**插件机制与宿主生命周期的边界**没打通。这次的关键一跃，是把"插件收不到 Want"转化为"宿主转发 Want"——代价是文档里必须把集成步骤写透。
